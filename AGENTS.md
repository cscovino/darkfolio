# AGENTS.md — Darkfolio

Operational rules for the coding agent. Project philosophy canon: `.planning/PROJECT.md` · `PLAN.md` · `ROADMAP.md`.

## Project

16-bit RPG-style portfolio (Astro 7.3.5 + Phaser 4.2.1 + TypeScript ^5): visitors explore a 3-room dark house and discover content (projects, skills, contact) via CRT-overlay screens triggered by interactable objects. Astro pages host the Phaser game and also render inside the in-game overlay.

```

public/assets/  # sprites/, tilesets/, audio/, maps/ (PNG + OGG)
.planning/      # project canon (committed): PROJECT · PLAN · ROADMAP · STATE · REQUIREMENTS · config
.github/        # PULL_REQUEST_TEMPLATE.md
```

## Working directories

- Source under `src/`. Assets under `public/`. Vitest tests co-located as `*.test.ts`.
- `.planning/` is the canonical project state — committed; do not hand-edit, use `/gsd-*` commands.
- `.opencode/`, `.astro/`, `dist/`, `node_modules/`, `coverage/` — gitignored; exception: `.opencode/agents/team/` and curated `.opencode/skills/` dirs (Phaser/astro/pixel-art) are tracked; `gsd-*` stays ignored (regenerated by gsd install).
- Do not commit `pnpm-lock.yaml` deletions or `.codegraph/` edits without approval.

## Commits

Format: `<emoji> <type>(<scope>): <subject>` — emoji table in `.planning/PLAN.md` §"Commit Format".

- One line. ≤72 chars. No body.
- Subject references code only — file path, directory, or symbol.
  Never mention `.planning/`, `.gsd/`, `.opencode/`, `.codegraph/`, `AGENTS.md`, plans, phases, or any plugin/integration (ponytail, biome, husky, vitest, GSD, …).
- No `Co-Authored-By:` trailers. No AI sign-off.
- Types: feat · fix · refactor · perf · test · docs · style · chore · build · ci.
- Scope = top-level source dir the diff touches. Standard set: `game`, `pages`, `layouts`, `components`, `styles`, `content`, `config`, `deps`, `tests`, `hooks`, `ci`, `planning`. Single-file change: file's directory.

Example: `✨ feat(game): add player movement in src/game/objects/Player.ts`

## Squash discipline

After every feature, fix, OR plan completion, the agent checks: can the recent commits be one commit and still be reviewable? Squash toward the fewest number of commits possible — but evaluate every fold from the reviewer's seat: fewer commits is the goal only when the reviewer can still follow the change in one read.

**Before opening any PR** (rule): treat `git log --oneline main..HEAD` as draft state — trim it to the fewest reviewable commits, grouped per subsystem, before the PR exists. Reviewers read branch history, so the trim is a PR-creation prerequisite, not post-review cleanup.

**Squash when:**
- Multiple commits touch the same directory/scope and form one logical change — e.g. three small edits inside `game/Player.ts`.
- A commit only reverts or fixes the previous one — use `git commit --fixup=<sha>` so rebase auto-folds.
- The branch is not yet pushed, so no reviewer depends on the granular history.

**Keep separate when:**
- Distinct subsystems (e.g. `game/player` vs `game/audio`) — each deserves an isolated review.
- A commit deliberately bisects a bug — preserve for `git bisect`.
- A commit is already reviewed individually via PR comments — don't lose that trail.
- Conflicting build states (a commit in the middle doesn't compile; don't fold it).

**Practical:** `git log --oneline -10` to inspect, then `git rebase -i HEAD~N` (interactive) or `git reset --soft HEAD~N && git commit` for a clean re-squash. The rewritten message keeps the conventional+gitmoji+code-only rule.

When in doubt: keep separate. Over-fragmented is cheaper than under-fragmented.

## Code comments

- Only when truly necessary and super concise — the code itself must be self-explanatory.
- JSDoc where it adds value (exported/non-obvious functions); skip trivial signatures.
- Comments reference code only: never name plugins or tooling, never plan numbers, never phase names.

## Branches & PRs

- Trunk: `main`. Work on a dedicated branch.
- Branch names start with an intent prefix — `feat/<slug>`, `fix/<slug>`, or `refactor/<slug>` (e.g. `feat/player-movement`, `fix/crt-overlay`). The prefix declares the branch's purpose before anyone opens the diff. Never use plan/phase machinery in names — no `phase-N`, plan numbers, or GSD terminology; the roadmap in `.planning/` owns phase↔branch bookkeeping, not the branch name.
- Open a PR to main. PR title = commit subject. Squash-merge.
- PR title and body reference code and purpose/intent only — never plan numbers, phase names, or GSD terminology.
- PR uses `.github/PULL_REQUEST_TEMPLATE.md`.

## Pre-commit gate

Every commit must satisfy all four before it lands:

1. `pnpm format` — Biome formatter clean.
2. `pnpm test` — Vitest passes.
3. `pnpm exec astro check` — typecheck passes.
4. `pnpm build` — production build succeeds.

For pure logic (= systems, data, helpers): **TDD-lite** — write the failing vitest case first, then implement until it passes. For Phaser scenes, Astro pages, and assets: test internals where separable, verify visually via `pnpm dev`.

## Post-fix hook (always)

After every feature OR fix passes the gate, run the **ponytail audit** on the diff and apply its simplifications before declaring done.

## Pre-verification hook (always)

Before the **first** `/gsd-verify-work {phase}` of a phase (not on a resume), the branch must be trimmed to its final shape — so the verification report is generated against the code that actually ships, and its digest stays fresh.

1. **Audit** — run the **ponytail audit** on the whole tree (not a diff).
2. **Apply** — apply the findings. Anything that would break a locked decision (D-xx), a canonical file list in `.planning/PLAN.md`, or an already-verified artifact is **skipped with a one-line reason and surfaced to the user** — never silently dropped, never silently applied.
3. **Gate** — re-run the §"Pre-commit gate" after the changes.
4. **Squash** — trim `main..HEAD` to the fewest reviewable commits, grouped per subsystem, per §"Squash discipline". Do this *before* the verification artifacts exist, so no report has to be regenerated afterwards.
5. **Verify** — only then run `/gsd-verify-work {phase}`.

Skipping steps 1–3 leaves the report covering code that no longer exists (`verification.status` → `stale`, route `execute-phase`). Skipping step 4 hands the reviewer a 40-commit branch instead of a readable one.

## Always

- Use path aliases (`@/game/...`) per `.planning/PLAN.md` §"Path Aliases".
- Add new deps from §"Tech Stack" only — surface anything new to the user first.

## Never

- Add features not in `.planning/REQUIREMENTS.md` §"Out of Scope" — re-read before each phase plan.
- Add deps not in `.planning/PLAN.md` §"Tech Stack".
- Write "what"-comments. Comments only when the *why* is non-obvious.
- Abstract single-use code.
- Add error handling for impossible scenarios.
- Write tests for trivial functions (pure getters, type re-exports).
- Add configuration for things that cannot change at runtime.
- Edit `AGENTS.md`, `.planning/`, `.opencode/`, `.codegraph/`, `pnpm-lock.yaml` without asking.

## GSD workflow

This repo runs the GSD (Get-Shit-Done) workflow on top of the operational rules above.

- `/gsd-progress` — start here to read state.
- `/gsd-discuss-phase N` — clarify approach for phase N before planning.
- `/gsd-plan-phase N` — decompose a phase into executable plans.
- `/gsd-execute-phase` — run plans in parallel waves.
- `/gsd-verify-work` — validate after execution. Run the §"Pre-verification hook" first (audit → apply → gate → squash).
- `/gsd-complete-milestone` — archive and reset at milestone boundaries.

Quick reference lives in `.opencode/skills/gsd-*`. Always read `.planning/STATE.md` first to recover session context.
